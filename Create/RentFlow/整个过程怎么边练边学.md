这些部分不要完全交给代码生成：
- 数据库表之间的关系
- 订单状态转换
- 时间冲突判断
- JWT 登录流程
- 权限控制规则
- Service 事务边界
- 缓存 Key 设计
- 并发预约方案
- 测试用例
- README 中的技术说明
页面样式、重复 DTO、普通 CRUD 可以适当借助工具提高效率，但核心业务必须自己理解。

每个功能都使用下面这套循环。

## 第一步：先写业务规则

例如准备写“取消预约”，先回答：

```
什么状态可以取消？
谁可以取消？
预约开始后还能取消吗？
取消后器材如何释放？
重复取消怎么办？
```

## 第二步：设计输入和输出

```
PUT /api/bookings/{id}/cancel
```

思考：

- 是否需要 RequestBody
- 返回什么
- 失败使用什么状态码
- 如何确认当前用户有权取消

## 第三步：设计数据库变化

```
booking.status：RESERVED → CANCELLED
equipment是否需要改变状态
是否生成操作日志
是否需要事务
```

## 第四步：只学习当前需要的知识

例如取消操作需要事务，就集中学习：

- `@Transactional`
- 什么异常会回滚
- 事务应该加在 Service 哪里
- 为什么不能加在 Controller

不要因为遇到事务，就一次学习完分布式事务、Seata 和两阶段提交。

## 第五步：自己先实现最小版本

建议顺序：

```
Mapper
  ↓
Service
  ↓
Controller
  ↓
接口测试
```

核心业务尽量先自己写。我可以帮你：

- 解释需求
- 检查设计
- 提示需要的知识
- 审查代码
- 分析错误
- 补充测试
- 比较不同方案

但不建议一开始让我直接生成整个模块，否则代码能运行，你却不容易真正掌握。

## 第六步：测试三类情况

每个接口至少测试：

```
正常情况
边界情况
错误情况
```

重要功能再测试并发情况。

## 第七步：总结并提交 Git

每完成一个小功能就提交：

```
feat(auth): implement JWT login
feat(equipment): add equipment pagination query
feat(booking): prevent overlapping reservations
fix(order): reject pickup of cancelled orders
test(booking): add concurrent booking test
```

然后用自己的话记录：

```
这个功能解决了什么问题？
为什么这样设计？
遇到了什么错误？
还有什么不足？
```
